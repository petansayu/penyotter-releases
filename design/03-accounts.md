# 3. アカウントと署名

対象の版: 0.186.0

## 3.1 アカウントの種類

端末にはアカウントをいくつでも入れられ、画面の上で切り替えます。アカウントは次の 4 種類です。

| 種類 | 入れ方 | 秘密鍵の置き場所 | 署名 | 暗号化・復号 |
|---|---|---|---|---|
| 秘密鍵 | `nsec1…` を貼る、`ncryptsec1…` とパスワード、またはアプリで新しく作る | この端末（暗号化して保存） | アプリ内 | アプリ内 |
| 署名アプリ（NIP-55） | 端末の署名アプリを選ぶ | 署名アプリ | 署名アプリ | 署名アプリ |
| リモート署名（NIP-46） | `bunker://…` を貼る | リモート署名の側 | リレー経由で頼む | リレー経由で頼む |
| 閲覧専用 | `npub1…` か NIP-05（`名前@ドメイン`）を入れる | なし | できない | できない |

- 同じ公開鍵がすでに署名できる種類で入っていれば、閲覧専用として入れ直しても署名できる種類のままにします。
- 閲覧専用のアカウントは、ホームを最初から「フォロー中」にします。DM は読みません（5.7）。投稿・リアクションなど、署名が要る操作はできません。
- `nostrconnect://`（NIP-46 でアプリの側から接続を始める方法）には対応していません。

## 3.2 秘密鍵のアカウント

- 秘密鍵は、端末の Android Keystore で作った AES-GCM の鍵で暗号化して保存します。Keystore の鍵はアカウントごとに作り、端末の外に出せません。
- 署名や暗号化のたびに秘密鍵を取り出し、使い終わったらメモリ上の値を 0 で上書きします。
- 署名は BIP-340 の Schnorr 署名です（secp256k1 のライブラリ）。署名の前に、取り出した秘密鍵から公開鍵を作り直し、アカウントの公開鍵と一致することを確かめます。
- 新しく作るときは、端末の安全な乱数で 32 バイトを作ります。作った直後に nsec を表示し、その場で ncryptsec でも書き出せるようにしています。
- 秘密鍵は nsec か ncryptsec で書き出せます。

### ncryptsec（NIP-49）

- 読み込み・書き出しとも、版は 2 だけに対応します。
- 鍵の導出は scrypt（r = 8、p = 1、N = 2^logN）です。パスワードは NFKC で正規化してから UTF-8 にします。読み込むときの logN は 16〜22 だけを受け付けます。書き出すときは logN = 16 です。
- 暗号は XChaCha20-Poly1305 で、鍵の安全性の 1 バイトを追加データにします。書き出すときの値は 2（この鍵の扱いの経緯は分からない、の意味）です。

### アカウントの画面の撮影

アカウントの追加（ログイン・新しく作る）の画面と、秘密鍵（nsec・ncryptsec）を表示する画面は、Android の撮影の禁止（`FLAG_SECURE`）を付けています。スクリーンショットや画面の録画、最近使ったアプリの一覧の縮小画面に、秘密鍵が写らないようにするためです。

## 3.3 署名アプリ（NIP-55）

### ログイン

1. 端末で `nostrsigner:` を開けるアプリを探します。1 つならそれを、いくつかあれば選んでもらいます。
2. 選んだアプリを名指しして（`setPackage`）、`get_public_key` の Intent を送ります。`permissions` には、このアプリが署名する kind の一覧と、NIP-04・NIP-44 の暗号化・復号を入れます。
3. 返ってきた公開鍵は、16 進でも npub でも受け付けます。どのアプリが答えたかを、アカウントに結び付けて覚えます。

### 署名の頼み方

1. まず ContentProvider（`content://<署名アプリ>.SIGN_EVENT`）で、画面を出さずに頼みます。署名アプリで「常に許可」にしていれば、ここで返ります。
2. 返らなければ、Intent で署名アプリの画面を開いて頼みます。
3. 返ってきたイベントは、署名を確かめ直し、頼んだ中身（作者・時刻・kind・タグ・`content`）と一致することを確かめます。署名だけが返ったときは、頼んだ中身に付けて確かめます。
4. 結果に `rejected` があれば、拒否として扱います。Amber は拒否を、成功の結果（`RESULT_OK`）に `rejected` を付けて返すことがあるためです。

例外として、リレーの認証（kind 22242）は 2 に進みません（4.2.2）。

### 暗号化・復号の頼み方

| 何を | 画面を出すか |
|---|---|
| DM の一覧の復号 | 出さない。ContentProvider で返らなければ、その分は読めない |
| 暗号化（DM の送信、リレーへの下書きの保存など） | ContentProvider で返らなければ出す |
| リレーの下書き（NIP-37）・非公開のリストの復号 | ContentProvider で返らなければ出す |

DM の一覧の復号で画面を出さないのは、メッセージの数だけ画面が出てしまうからです。

## 3.4 リモート署名（NIP-46）

### ログイン

1. `bunker://<リモート署名の公開鍵>?relay=…&secret=…` を読みます。`relay` は `wss://` のものだけを使い、1 つもなければ受け付けません。
2. この端末用のクライアント鍵を作ります。秘密鍵と同じ方法で暗号化して保存します。
3. `connect`（リモート署名の公開鍵と `secret`）を送り、最大 120 秒待ちます。
4. `get_public_key` で利用者の公開鍵を受け取り、そのアカウントとして登録します。

### やり取り

- 頼むごとに、ランダムな ID の要求を NIP-44 で暗号化し、クライアント鍵で署名した kind 24133 として、リモート署名のリレーへ送ります。
- 送る前に、そのリレーで `{"kinds": [24133], "authors": [<リモート署名>], "#p": [<クライアント鍵>], "since": <10 秒前>}` を購読しておき、同じ ID の答えを待ちます。答えは NIP-44 で読み、読めなければ NIP-04 で読みます。
- `result` が `auth_url` の答え（別の場所で承認を待っている知らせ）は、飛ばして次の答えを待ちます。
- 待つ時間は、署名と暗号化が 120 秒、復号が 20 秒です。

## 3.5 署名する前に足すもの

どの種類のアカウントでも、署名の直前にクライアントタグを足します（6.1）。このため、署名アプリやリモート署名に見せる中身にも、クライアントタグが入っています。
