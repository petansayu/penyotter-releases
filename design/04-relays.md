# 4. リレーの扱い

対象の版: 0.186.0

この章では、自分のリレーの持ち方、リレーとの接続、相手のリレー（NIP-65 のアウトボックス）の使い方を書きます。画面ごとにどこから何を読むかは [5 章](05-reading.md)、何をどこへ送るかは [6 章](06-writing.md) にあります。

## 4.1 自分のリレーの設定

リレーの設定はアカウントごとに持ちます。

| 種類 | 件数 | 公開するか | 使い道 |
|---|---|---|---|
| 読み込みリレー | 1〜12 | kind 10002 に載せる | 自分宛ての通知、グローバル、反応数の問い合わせ、相手のリレーが分からないときの代わり |
| 書き込みリレー | 1〜12 | kind 10002 に載せる | 自分のイベントの送り先 |
| 検索リレー | 0〜12 | 載せない | NIP-50 の検索。相手の kind 10002 を探すときにも使う |
| グローバルのリレー | 0〜12 | 載せない | グローバルのタイムライン |
| DM 受信リレー | 1〜3 | kind 10050 に載せる | NIP-17 の DM を受け取る先 |

- URL は `wss://` だけを受け付けます。ユーザー名・パスワード入りの URL や `#` の付いた URL は受け付けません。末尾の `/` は取り除きます。
- 新しいアカウントの最初の設定は、読み込み・書き込みとも `wss://yabu.me`、`wss://relay-jp.nostr.wirednet.jp`、`wss://nos.lol` です。
- 常時接続リレーは、読み込みリレーの先頭から N 件です（既定 6 件、1〜12 件）。残りの読み込みリレーは、一回きりの取得のときだけつなぎます。
- グローバルのリレーの候補として、画面の言語が日本語のときだけ日本のリレー 3 件（yabu.me、relay-jp.nostr.wirednet.jp、r.kojira.io）を出します。グローバルのリレーを変えると、それまでに端末に保存したグローバルの投稿は消します。前のリレーの投稿が一覧の下に残らないようにするためです。

### 4.1.1 kind 10002 との同期

アプリは、リレーリスト（kind 10002）を勝手に取り込んだり、勝手に上書きしたりしません。

**起動したとき**
1. 読み込みリレーから自分の kind 10002 を取得します（`limit: 5`）。取得が「完了」（4.3）しなかったら何もしません。
2. いちばん新しいもの（`created_at` が大きいもの、同じなら ID が小さいもの）を選び、端末の一覧の履歴に記録します（7 章）。
3. 前に取り込んだもの、または「取り込まない」と選んだものと同じ ID なら、何もしません。
4. 中身が今の設定と同じなら、その ID を「取り込み済み」として覚えます。
5. 違っていたら、設定は変えずに「プロフィールのリレーリストに変更があります」と知らせます。取り込むかどうかは利用者がリレー設定の画面で選びます。

**公開するとき**
1. 読み込みリレーと書き込みリレーの両方から、自分の kind 10002 を取り直します。取得が完了しなければ公開しません。
2. ほかのアプリで更新されたもの（覚えている ID と違い、取り込んだ時刻より新しいもの）があれば公開をやめ、先にそちらを確かめるよう知らせます。
3. 新しい kind 10002 を作ります。`r` タグは、読み込みと書き込みの両方なら `["r", <URL>]`、片方だけなら `["r", <URL>, "read"]` / `["r", <URL>, "write"]` です。前の版の `r` 以外のタグと `content` は、ほかのアプリの情報なので残します。`created_at` は、今の時刻と、前の版の `created_at` + 1 のうち大きいほうです。
4. 署名の前に、前の版と新しい版を端末の一覧の履歴に保存します。保存できなければ送りません。
5. 書き込みリレーへ送ります。

検索リレーとグローバルのリレーは kind 10002 に載せません。

## 4.2 接続

- 1 つのリレーにつき WebSocket は 1 本です。タイムライン・プロフィール・通知・スレッドなどの REQ は、同じ接続に相乗りします。
- 接続の待ち時間は 10 秒、ping は 25 秒ごとです。
- 使われなくなった接続は 60 秒残してから閉じます。続けて別の取得が来たとき、つなぎ直さずに済むようにするためです。
- 切れたら、1 秒・2 秒・4 秒…と倍にしながら（32 秒まで）、0〜0.5 秒をランダムに足して、つなぎ直します。つなぎ直したら、残っている REQ と、受理を待っている EVENT を送り直します。
- 次のリレーは 3 分間「使えない」とみなし、一回きりの取得ではつなぎません（購読と送信は試します）。
  - HTTP の応答（502、404 など）が返ってきた、またはホスト名が引けなかった
  - 2 回続けて接続に失敗した
  - 一回きりの取得で、打ち切り（9 秒）まで EOSE もイベントも返さなかった
- 1 つのメッセージが 256,000 文字を超えたとき、または受信の処理が追いつかなくなったとき（512 件）は、その接続を切ってつなぎ直します。
- 購読ごとの受け取り口は 4,096 件までためます。あふれたら古いものから捨てます。

### 4.2.1 受け取ったイベントの確かめ方

リレーから届いた EVENT は、次をすべて満たすものだけを使います。満たさないものは黙って捨てます。

- `id`・`pubkey` が 64 桁、`sig` が 128 桁の小文字の 16 進
- `id` が NIP-01 の直列化の SHA-256 と一致し、Schnorr 署名が正しい
- `created_at` が 0 以上で、端末の時刻 + 10 分より前
- `kind` が 0〜65535
- `content` が 64,000 文字以下、タグが 4,000 個以下、タグの値がすべて文字列
- NIP-40 の `expiration` を過ぎていない
- その REQ のフィルタに合っている（リレーがフィルタと違うものを返しても使わない）

### 4.2.2 認証（NIP-42）

リレーから `AUTH` が届くと、そのとき使っているアカウントで kind 22242（`["relay", <URL>]`、`["challenge", <文字列>]`）に署名して送ります。`OK` で受理されたら、その接続の REQ と未受理の EVENT を送り直します。

アカウントの種類によって次のように変わります。

| アカウント | 認証 |
|---|---|
| 秘密鍵を端末に保存 | 自動で署名して答える |
| 署名アプリ（NIP-55） | 署名アプリが画面を出さずに答えたときだけ。画面を開いて頼むことはしない |
| リモート署名（NIP-46） | リモート署名に頼む（最大 120 秒待つ） |
| 閲覧専用 | 答えない |

NIP-55 で画面を開かないのは、つなぐたびに署名アプリの画面が出てしまうからです。署名アプリで AUTH を「常に許可」にしていない人は、認証が必要なリレーから読めない分があります。`challenge` が空、または 1,024 文字を超えるときは答えません。

## 4.3 一回きりの取得

一覧の読み込み、「さらに読む」、ID での取得などは、一回きりの取得です。複数のリレーへ同じ REQ を送り、次の規則で終えます。

1. 3 分間「使えない」とみなしたリレーには送りません。
2. すべてのリレーが EOSE を返したら終わります。
3. 最初の EOSE が届いてから、それまでにかかった時間（少なくとも 1 秒）待って、残りのリレーを打ち切ります。
4. 全体で 9 秒たったら打ち切ります。
5. 同じ ID のイベントは 1 つにまとめ、どのリレーから届いたかを覚えます（投稿の詳細でリレーの一覧として出します）。

結果には「完了したか」が付きます。完了とみなすのは、送ったすべてのリレーが EOSE を返したとき、または 3 で打ち切ったときに半分以上のリレーが EOSE を返していたときです。一覧の書き換え（フォロー、ミュートなど）は、取得が完了したときだけ行います（7 章）。

### 4.3.1 さかのぼって読むとき

過去の投稿は `until` を下げながら読みます。

- 最初は `limit: 100` です。
- 返ってきたいちばん古い `created_at` が `until` より古ければ、それを次の `until` にします。`until` を含めて読むので、同じ時刻の投稿を取りこぼしません。
- 返ってきた全件が `until` と同じ時刻で、件数が `limit` に達していたら、`until` を動かさずに `limit` を倍にします（3,200 まで）。それでも足りなければ、「同時刻の投稿が多いため、これ以上の取得を停止しました」と出して止めます。
- 件数が `limit` に届かなければ、いちばん古い時刻 − 1 を次の `until` にします。
- 2 回続けて 1 件も返らなかったら、終わりとみなします。
- 取得が完了しなかった回は、`until` を動かしません（もう一度同じ範囲を読めます）。

## 4.4 相手のリレー（アウトボックス）

ほかの人の投稿やプロフィールは、なるべくその人の kind 10002 の書き込みリレーから読みます。

### 4.4.1 相手の kind 10002 の探し方

- 探す先は、渡されたリレーのヒントと、自分の常時接続リレー・検索リレーです（合わせて 6 件まで）。
- 何人分かまとめて探すときは、200 人ずつ、同時に 3 つまで問い合わせます。
- いちばん新しい kind 10002 の `r` タグを読みます。3 つ目の値が `read`・`write` 以外の `r` タグは使いません。12 件までです。
- `wss://` 以外、`localhost`、`127.`・`10.`・`192.168.`・`172.16〜31.` で始まるアドレスは使いません。相手のリストで端末を家のネットワークへ向けさせないためです。
- 書き込みリレーは 6 件まで使います。
- 結果は端末に保存します。見つかったら 6 時間、見つからなかったら 10 分使います。自分のリレーリストを変えたら、自分の分は捨てます。

### 4.4.2 一人の投稿を読むとき

1. 相手の書き込みリレー（ヒントがあれば先頭に足す）へ REQ を送ります。
2. 0.7 秒後に、そこに含まれない自分の読み込みリレーへも同じ REQ を送ります。
3. 2 つの結果を合わせます。

### 4.4.3 何人もの投稿を読むとき

フォロー中のタイムラインなどです。

1. 相手を 500 人までにし、それぞれの書き込みリレーを調べます。
2. リレーごとに相手をまとめ、相手の多いリレーから 12 件を選びます。1 つの REQ の `authors` は 100 人までにします。
3. 選んだリレーへ、同時に 8 つまで問い合わせます。1 つあたり 4 秒で打ち切ります。
4. 0.7 秒後に、常時接続リレーへ全員分の REQ を送ります（取りこぼしを防ぐため）。
5. すべての結果を合わせます。

購読するときも同じ分け方をします（4 秒の打ち切りはありません）。

この方法では、選ばれた 12 件のどれにも書いていない人の投稿は、常時接続リレーにあるときだけ読めます。

ただし、ホームのフォロー中では、自分の書き込みリレーには 12 件とは別に必ず問い合わせます（0.186.0 の次の版から）。それまでは、自分の書き込みリレーがフォロー中の人とあまり重ならず、読み込みリレーにも入っていないと、自分の投稿がホームに出ませんでした。

## 4.5 送信

1. 送り先のすべてのリレーへ EVENT を送ります。つながっていないリレーは、つながってから送ります。
2. どれか 1 つが受理するか、すべてが答えるか、12 秒たつと、その時点の結果を返します。
3. 受理されたあとも答えていないリレーがあれば、さらに最大 12 秒待ち、後から届いた答えで「x/y リレーが受理しました」の表示を直します。

結果は、リレーごとに「受理」「拒否」「確認できない」のどれかです。どこも受理せず、確認できないリレーがあるときは「届いている可能性があります」と出します。

署名したイベントは、送る前に端末に保存します。再送するときは同じイベント（同じ ID と署名）を送ります。何度送っても、リレーから見ると同じイベントです。

送り先の決め方は [6 章](06-writing.md) にあります。

## 4.6 件数（NIP-45）

フォロワー数だけ、`COUNT` を使います。読み込みリレーそれぞれに専用の接続を開き、5 秒で打ち切ります。答えたリレーのうちいちばん大きい数を使い、どれかが `approximate: true` を返したら、その数をおよその数として扱います。どのリレーも答えなければ数は出しません。
